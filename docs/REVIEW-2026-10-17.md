# Herdr PWA review — 2026-10-17

The project has useful foundations: separate sources for content and control, a shared runtime API contract, bounded initial reads, incremental cursors, adapter fixtures, and explicit uncertainty around actions. The next investment should address conversation isolation, correctness, and repeated work. A Rust backend is a viable direction, but this review provides no measured Rust speedup.

This is a review, not an implementation. No input was sent to any agent, no agent was started, and no live conversation was opened. Checks used the existing mocked suite, server-side React rendering, and temporary session files. Interactive browser inspection failed because the computer-use connection could not find the browser window. Stored screenshots are historical and are not evidence of the current layout.

## Findings, in priority order

### 1. Local action state can cross conversation boundaries — P0, code traced

`apps/web/src/App.tsx:569` renders the same `ChatScreen` component when switching between neighboring panes, without a pane identity key. `ChatScreen.tsx:103` stores local sends in component state; those objects contain no destination pane. Only the draft is explicitly restored per pane (`:660`). Local sends, answer state, free-answer mode, and several other controls have no equivalent reset or per-pane ownership.

The concrete dangerous sequence is: a failed/uncertain message exists in A, switch to B using the pane strip, then retry that message. The preserved bubble calls the current `reessayerEnvoi` (`:854`), whose `transmettre` closure sends to the current `agent.paneId` (`:666`). That can route A's retry into B. This was traced without sending any request. It needs a fully mocked mounted-component regression before release.

Session loading has a related race (`:196`): a request started for A can resolve after the props change to B and write A's entries and cursor into the shared component state. There is no abort or request-generation check. The shared `loading` ref can also prevent B's initial load while A remains in flight.

**Change:** make destination identity immutable on every local action, own conversation state by pane plus session identity, and reject stale asynchronous results. A keyed screen can isolate transient UI, but pending sends must survive navigation in a separately owned, destination-bound store. Simply adding a key would currently cancel the 900 ms queued-send timer on unmount after the draft has already been cleared.

### 2. Partial JSONL lines corrupt incremental summaries — P1, reproduced

`apps/server/src/sessions/SessionReader.ts:306` prepends `pending` while reading again from an offset that already points to the beginning of that pending fragment. `apps/server/src/conversations/Summary.ts:616` supplies both values. The bytes are duplicated.

An isolated fixture containing one complete line and `{"type":` was read, then completed with `"message","id":"b"}\n`. Reading again through `defaultRead` produced one `unknown` entry and offset **64 for a 56-byte file**. This corrupts the derived read, not the source file; subsequent reads can skip content or reset incorrectly. The session HTTP route generally passes an empty pending string, so the reproduced path is the conversation-summary cache.

**Change:** choose one offset convention: either reread the incomplete fragment with an empty pending string, or read after the stored fragment and prepend it exactly once. Cover split UTF-8, repeated partial appends, truncation, and rotation. The incremental read also allocates the entire appended remainder (`SessionReader.ts:303`), so a reconnect has no byte ceiling comparable to the initial tail. Add bounded incremental pages with explicit continuation.

### 3. PWA updates can discard drafts and pending actions — P1, code traced

`apps/web/src/main.tsx:31` reloads immediately on `controllerchange`. Drafts live in a module-local `Map` (`brouillons.ts:19`), and local delivery state lives in React. `vite.config.ts` enables immediate worker activation and claiming. The comment asserting updates do not interrupt typing does not match this reload handler.

**Change:** defer reload while drafts or unresolved actions exist, then offer an explicit update action. If persistence is desired, define its lifetime and privacy behavior first. Preserve uncertain delivery state across any allowed reload so reconnecting cannot encourage an accidental duplicate send.

### 4. Markdown tables render without content — P1, reproduced

`apps/web/src/Markdown.tsx:159` passes table cells and row arrays through `tokenList`, which requires a `type` field. Marked table cells and row arrays do not meet that condition. Both the header and body are discarded.

Server-rendering `| Name | Value |\n| --- | --- |\n| sample | 42 |` produced `<thead><tr></tr></thead><tbody></tbody>`.

**Change:** validate table cells and row arrays according to their actual shapes and add a rendered-output check for their text. Keep the existing safe React rendering of untrusted Markdown.

### 5. Blocked agents say “working” — P1, reproduced

`apps/web/src/ConversationRow.tsx:43` handles unknown, done, and idle; blocked falls through to `return "working"`. A fixture with status blocked rendered `<span class="etat etat--bloque">working</span>`. The color and the text disagree precisely when a person needs to act.

**Change:** handle every status explicitly. Separately, idle entries with any timestamp are labeled “finished”; a last session event is not necessarily verified completion. Use last-activity wording when completion is not known.

### 6. SSE disconnect cleanup and restart replay are incomplete — P2, reproduced

In `apps/server/src/http/routes-events.ts:57`, the polling loop's `closed` variable is local to `start`. `cancel` (`:96`) releases the stream counter without stopping the loop. With an empty mocked journal, canceling a reader left polling active: **one journal read at cancellation, three after another 700 ms**. It eventually errors if another event is enqueued, but otherwise continues. The released counter does not bound those orphan loops.

`apps/server/src/events/EventHub.ts:66` detects cursors older than its retained journal, but not cursors ahead of a restarted journal. After creating a new hub and publishing event 1, `since(500)` returned no events and `resyncRequired: false`. Native reconnect can therefore miss new events until IDs catch up. Frontend periodic refresh reduces the visible impact but does not repair the stream guarantee.

**Change:** cancel the subscription task on disconnect, use an actual event subscription rather than per-client 300 ms polling, add heartbeats and bounded slow-consumer behavior, and include a server epoch in replay identity or explicitly resync future cursors. Recreating an EventSource also needs an explicit resync/replay policy because a new instance does not inherit its predecessor's Last-Event-ID.

### 7. Viewing a conversation changes desktop focus — product issue, code traced

`apps/web/src/ChatScreen.tsx:358` calls `focusAgent` on opening and every agent status change. `apps/web/src/api.ts` documents that this changes the actual Mac pane focus. It also acknowledges a done agent by changing its status. This ties reading on the phone to desktop interaction, and the effect is not visibility-gated.

**Change:** track local unread/read state independently of Herdr status. Make desktop focus an explicit action. Preserve the difference between “I read this” and “the agent is idle.” This automatic effect is why live conversations were not opened during the audit.

## Where the performance work should go

The following are code-derived costs, not runtime benchmark results:

- **Overlapping data acquisition.** `App.tsx:218` requests overview, health, and conversations every four seconds (`:247`), including while a chat is open, and also refreshes on every agent-status event. Overview's warm-cache path still calls `herdr.snapshot` (`Api.ts:591`), as does conversations (`routes-conversations.ts:219`). The watcher also takes a snapshot every two seconds. A busy chat requests its session every 400 ms when visible. At fast response times that is roughly 195 application GETs/minute per visible working chat, before SSE-triggered refreshes. Hidden chat polling slows down, but the App interval does not explicitly adapt to visibility.
- **No shared in-flight refresh.** The App counter prevents a premature loading indicator, but does not coalesce requests or prevent an older response overwriting newer data. `Promise.all` also prevents a successful conversation response from being committed if health or overview fails.
- **Synchronous session discovery.** Codex and Claude IDs trigger uncached recursive `globSync` searches (`SessionLocator.ts:101,144`). Conversations resolve sources during filtering and again during row construction. This work grows with the session archive and blocks the JS event loop.
- **Synchronous SQLite reads.** The SQLite adapters repeatedly open and close databases and set a three-second busy timeout (`OpencodeReader.ts:61`; Devin has the same pattern). Bun documents this API as synchronous. Lock waits and query work can delay unrelated requests; concurrency wrappers do not make synchronous work asynchronous.
- **Unbounded rendered history.** `ChatScreen.tsx:126` derives touched files on each render, and `:1079` rebuilds grouped items in JSX. `Blocks.tsx:979` maps the entire loaded history. Typing can therefore trigger history-wide work despite memoized Markdown. Incremental entries and rendered messages also remain in memory together. Profile first, then isolate the composer, memoize derived history by actual dependencies, and window long conversations while preserving scroll anchors and text selection.

Use one backend-owned snapshot and materialized conversation view, shared across clients. Cache session-ID resolution with invalidation, share in-flight reads, move blocking database work away from the request loop, and tail each actively observed source once. SSE should publish invalidation or content changes from those shared readers; the frontend should fetch cursor deltas, with slower polling as recovery. Watch session stores directly; do not assume Herdr implements content events it does not support.

Measure cold/warm p50 and p95 for list and session reads, discovery time, bytes parsed/returned, event-loop delay, CPU/RSS at idle and during streaming, and phone interaction latency. Use synthetic stores with 1/10/50 panes, large archives, partial writes, database locks, multiple clients, and reconnects. Add a boundedness check for bytes per response and pending event queues.

## Rust direction

A Rust backend is reasonable if lower daemon resource use, deployment simplicity, or isolation of parsing/database work are project goals. The current evidence does not establish that Bun HTTP dispatch is the bottleneck. Porting the same polling, discovery, and request ownership would preserve their costs and races.

If proceeding, structure the replacement around a shared state owner, source adapters, an incremental session index, a bounded event journal/fan-out layer, and a thin HTTP control layer. Tokio plus Axum is a suitable candidate; Axum directly supports streaming SSE and keep-alive messages. Keep blocking database operations outside asynchronous request execution, and handle lagged subscribers explicitly.

Preserve the existing HTTP behavior during migration. Export a language-neutral schema from the current contract and generate or validate both languages from it; do not hand-maintain a second Rust version of `api.ts`. Keep transport confirmation semantics, origin/path guards, read-only source access, and adapter fixtures. Use recorded synthetic fixtures to compare responses and cursors across implementations. Switch one read route at a time; migrate mutations only once their contracts and destination identity are covered. Do not mirror mutation traffic into both backends.

Sources: [Bun SQLite documentation](https://bun.sh/docs/runtime/sqlite), [Axum SSE documentation](https://docs.rs/axum/latest/axum/response/sse/).

## Webapp product direction

The strongest opportunity is making the app good at supervising work and making decisions from a phone. Recommendations below are design proposals, not claims about completed browser validation.

1. **Actionable home screen.** Keep attention-required and working groups, but distinguish an actual question, an unread completion, stale data, and idle. Show a short grounded result or question preview alongside the recognizable user request. Add search across project, agent, branch, and prompt; keep detailed filters optional.
2. **Reliable conversation workspace.** Give each conversation its own scroll anchor, draft, pending actions, and files/model sheet state. Make updates and reconnects preserve that workspace. Show a “new messages” jump action when someone is reading history; avoid moving their position automatically.
3. **Reviewable results.** Separate the final answer, current activity, changed-file summary, and artifacts. Keep detailed tools expandable. Label changes as inferred from session tools unless checked against the worktree; a session write log is not proof of the current diff. Add copy actions and readable code/table rendering.
4. **Desktop layout.** Introduce a responsive two-pane layout with a persistent searchable conversation list and a conversation/detail area. The current full-width single-column shell is optimized around phone navigation. Keep a single focused screen on mobile and validate keyboard/landscape states on a real installed iPhone.
5. **Truthful connection and action feedback.** Distinguish API reachability, content freshness, and event-stream connectivity. Display a concise visible stale-state explanation with a retry action. Keep confirmed receipt separate from application by the target agent.
6. **Accessible sheets.** `Feuille.tsx` implements a keyboard focus cycle on a nonmodal open dialog with `aria-modal`. Add background inertness and browser checks for screen-reader navigation, pointer interaction behind the sheet, Escape, and focus restoration. Source-text assertions cannot establish those behaviors.

## Suggested delivery sequence

1. Fix conversation/action isolation, partial-line accounting, update-time state loss, blocked labels, Markdown tables, and SSE lifecycle/replay. Protect them with behavior checks using fake transport only.
2. Consolidate data acquisition and add instrumentation. Compare fixed-workload performance before choosing the Rust scope.
3. Build the searchable supervision UI, stable conversation workspace, result/file review, and responsive desktop layout against the existing contract.
4. If Rust remains desirable, replace the backend incrementally using schema and fixture parity, and publish measured resource/latency differences.
